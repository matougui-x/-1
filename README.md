# 校园失物招领

一个纯前端的校园失物招领信息平台，实现「**发布信息 → 浏览/搜索 → 查看详情 → 联系发布者 → 更新状态**」这条完整主线。

这是《软件工程》第二次结对作业的代码实现，基于第一次结对作业的原型设计（手机端 375×812，主色 `#12A87A`，卡片圆角 14px），在同一套设计规范上扩展出了桌面端形态。

---

## 一、快速开始（三种方式任选）

### 方式 1：直接打开（推荐，零依赖）

下载全部文件后，**用谷歌浏览器打开根目录下的 `index.html`** 即可：

```
双击 index.html
  或
右键 index.html → 打开方式 → Google Chrome
```

不需要安装 Node.js，不需要起本地服务器，不需要联网。第一次打开会自动灌入一批演示数据，可以直接点击体验全部功能。

> 请使用 **谷歌浏览器（Chrome）**。其它浏览器也能运行，但 `file://` 协议下不同浏览器对本地存储的处理有差异（Firefox 会把每个本地文件当成独立来源，导致页面之间读不到彼此的数据），Chrome 是本次统一指定的测试环境。

### 方式 2：运行单元测试

**双击 `test/test.html`**，用 Chrome 打开，会自动跑完全部 262 个测试用例并显示绿色/红色报告。

### 方式 3：起一个本地服务器（可选）

如果你更习惯用 `http://` 访问，在项目根目录执行：

```bash
python -m http.server 8080        # Python 3
# 或
npx serve .                       # 需要 Node.js
```

然后访问 <http://localhost:8080/index.html>。

| **认领验证（防冒领）** | `publish.html` → `verify.html` | 拾得者出 3–5 道判断题/选择题，认领者一次答完，全对才看到联系方式，最多答 3 次 |

### 关于「公开特征」

原来每条信息的公开面是「标题 + 300 字自由描述 + 地点 + 时间」。那条自由描述是最容易出事的地方：**拾得者顺手就把特征写出来了**。演示数据里就有现成的例子——一条招领帖的公开描述写着"伞柄有一道划痕"，而它的验证题正好问"伞面上最明显的特征是［一道划痕／…］"，答案等于白送。同一批数据里还有：标题写「学号 2023\*\*\*\*」，验证题问"这张卡是哪个年级的"；标题写「内有笔记本」，验证题问"包里最显眼的物品是"。

所以现在**除了「其他」，每个分类对外只能露出字典里定死的 1–2 项**（见 `js/config.js` 的 `LF.FEATURES`）：

| 分类 | 公开特征① | 公开特征② |
| --- | --- | --- |
| 证件卡片 | 卡号（打码） | —— |
| 耳机 | 品牌 | 外观颜色 |
| 雨伞 | 伞面颜色 | 柄型 |
| 水杯 | 颜色 | 材质 |
| 电子产品 | 品牌 | 型号 |
| 包与书包 | 类型 | 颜色 |
| 衣物配饰 | 类型 | 颜色 |
| 眼镜 | 镜框材质 | 镜框颜色 |
| 其他 | **不锁**：保留自由描述框，也**不出验证题**（见下） | |

配套的四条规则：

- **自由描述框取消**。非「其他」分类在发布页不显示描述框，数据层也会强制把描述置空（`store.create` / `store.update`），不是靠前端隐藏。
- **特征必须填**。它已经顶替掉了描述，空着等于这条信息没人认得出。校验错误键带 `feat_` 前缀，与既有字段名隔离。
- **特征值参与搜索和筛选**。搜「华为」能命中那条华为耳机；列表页选中分类后，侧栏多出一组该分类的特征筛选。取值必须是字典里定死的白名单，否则没法做精确筛选。
- **没有特征可锁的分类，也不出验证题**。「其他」这一类见下一节。

#### 「其他」：对照组，走信任原则、不出验证题

前三条规则都建立在一个前提上：**这一类物品有客观、能锁死的细节**（品牌、颜色、卡号）。而「其他」之所以是「其他」，恰恰因为它没有——一本书、一串钥匙、一个说不清型号的充电器，硬要出题，出题人只能把描述里的细节再抄一遍：同一份信息写两次，还可能被冒领者照着公开描述选对。**在一类根本没有可锁特征的信息上要求出题，只会让人编题。**

所以「其他」走**信任原则**：**不设认领验证题**，描述和照片直接公开，联系方式直接可见，见到的人直接联系发布者核对。这一条由 `js/store.js` 的 `LF.allowVerifyFor()` 统一定，页面不自己判断分类名：

| 分类 | `allowVerifyFor` | 出题 | 谁看得到联系方式 |
| --- | --- | --- | --- |
| 有公开特征的八类 | `true` | 必须出 3–5 题 | 答对全部题目的人 |
| 其他 | `false` | **不出题** | 所有人（公开） |
| 字典里没有的分类（脏数据） | `null` | 不校验 | 分类字段自己已经报错了，不再叠加报错 |

落实在四处，且都是"数据层拦一道、页面讲清原因"：

- **数据层说了才算**。`store.create` / `store.update` 对「其他」强制把 `questions` 置空——前端就算传了题目也落不了盘；`needsVerify()` 对「其他」恒为 false，于是联系方式对所有访客直接可见，`startClaim()` 也会明确回"这条信息不需要验证"。
- **旧数据就地清掉**（`DATA_VERSION` 3 → 4）。演示数据 `seed_6` 原本给这一类挂着 4 道题，v3 时代的真实数据也可能有；迁移会把它们清空并把作答次数复位，否则发布者被永久锁在一个连编辑入口都没有的旧流程里。
- **发布页给出处**，不是把出题区一藏了事。选中「其他」时出题区换成一段说明：为什么不出题、描述和照片会直接公开、**代价**是没有防冒领闸门（所以别把唯一凭据写进公开描述）。切换分类时两者自动互斥。
- **详情页 / 我的发布 / 发布成功页**都顺手说一句"这一类没有验证题"，免得认领人以为页面坏了、发布者以为自己漏填了。

「其他」的搜索引导也顺势改成另一件事：它没有特征可筛，所以引导语说的是"翻列表、按地点找、翻到了直接联系发布者核对"，而不是"请按某某搜索"。

#### 告诉失主该搜什么

"一刀切"把信息面收窄之后，**新问题立刻跟着来了**：一条信息能命中的内容只剩标题、地点和那一两个特征，可失主并不知道。他还是会按习惯搜「蓝色充电宝」「伞柄有划痕」——这些词只存在于已经不再公开的描述里，于是搜出 0 条。而**"0 条结果"和"没人捡到"在页面上长得一模一样**，他会直接得出"东西没被人捡到"这个错误结论。信息收窄是为了防止泄漏，但如果不补上引导，代价就转嫁给了最着急的那个用户。

所以首页选中分类时，会在筛选区旁边（手机端在筛选条下面）显示一条该分类的引导语：

```
证件卡片 → 🔍 本类只公开卡号：请按证件号搜索（记不全的位用 * 顶位，位数要和卡号一样长），
            姓名、院系、卡号之外的细节都不公开。（卡号（打码））（就是全部可搜的公开特征）
其他     → 🔍 这一类不好指定公开特征，也不出认领验证题：发布者会把描述和照片直接公开，
            请翻列表（或用描述里的词、按地点）找，翻到了直接联系发布者核对。
```

三个细节值得说明：

- **八个分类各一条，「其他」另有一条**。引导语写在 `js/config.js` 的 `LF.CATEGORIES[].searchHint` 里，`LF.searchHintFor()` 只读这一份数据：有公开特征的分类讲"请按这几个特征搜"，「其他」讲"没有特征可筛，翻列表找"。没有写引导语的分类（以及脏数据里的未知分类）返回空串、页面不显示，所以页面不用维护一份分类名单。
- **不只是"请搜 X"，还要说清"搜不到什么"**。只告诉失主搜得动的字段，他不知道"颜色"根本不在公开面里，还是会去搜。所以每条引导语都带一句"哪些细节不公开"。
- **文案自带一句兜底**。`LF.searchHintFor()` 会检查 `searchHint` 里有没有提到字典里的字段名，没提到就把字段名附在后面。改了特征名却忘了改引导语时，现场自曝其短，而不是让失主照着过时的提示搜；`test/specs/validate.spec.js` 里有一组用例专门守这个（见"测试"一节）。

**原有的特征筛选按钮保留。** 引导语讲的是"关键词搜索该怎么搜"，而侧栏那组筛选按钮（点「华为」直接筛出华为耳机）本身就能用，两者互补：会搜的用搜索框，不会搜的点按钮。所以这里只加一句提示，没有删功能——`README` 与代码注释里都留着这条取舍。

#### 卡号为什么要打码

卡号是所有特征里最特殊的一个：它必须能被核对，又绝对不能公开。所以它不写成"只填前几位"，而是**写满总位数、最多露出 6 位数字，其余用 `*` 顶位**：

```
信息里存的是        350504************     （18 位，只露出前 6 位）

失主搜完整号码       350504200510291653   → 命中
不记得中间几位       35050420**********   → 命中（不记得的位用 * 顶）
只记得头尾          350504********1653   → 命中
原样把打码串粘回去    350504************   → 命中

位数不够           350504200            → 不命中
位数多一位          3505042005102916530  → 不命中
前 6 位记错          350505200510291653   → 不命中
```

匹配规则见 `js/store.js` 的 `LF.matchesWildcard`：**搜索词的位数必须和卡号完全一致**，然后逐位比较，**任意一边是 `*` 这一位就算过**。

- 模式里的 `*` = 拾得者没露这一位；
- 搜索词里的 `*` = 失主不记得这一位。

为什么非要位数一致：搜索词里也会出现 `*`，只有位数对齐了，"哪几位是我记得的"才没有歧义。允许短的话，`350504200` 到底是"前 9 位"还是"前 6 位 + 后 3 位"就说不清了。

打码位数是有代价的：露 6 位等于给出"前 6 位"这个筛选条件，露满就等于把证件号公开了。所以校验两头都拦：一位都不写（失主无从核对）和写超过 6 位都会被拒绝。

**搜索页会主动提示位数。** 位数对不上时结果是 0 条——而"0 条结果"和"没人捡到"在页面上长得一模一样，失主很可能就此以为东西没被人捡到，实际只是自己少打了一位。所以搜索页检测到关键词像证件号码时，会把两边的位数摆出来：

```
你填的是 6 位，库里的证件号码是 12 位。证件号码要按位数精确匹配，少一位多一位都搜不到。
```

位数对得上时则显示规则本身（位数要一样长、不记得的位写 `*`）。多个关键词的组合也认，比如搜「身份证 202305」同样会提示。

**搜索框右边还有一个实时计数。** 平时报"几个字"，一旦看起来像证件号码就改报"几位"，并按能不能对上库里的位数标绿标红——边打边能看见自己对不对得上，不用停下来数：

```
[🔍 202305          ] 6 位        ← 红色，库里是 12 位
[🔍 202305123456    ] 12 位       ← 绿色
[🔍 耳机             ] 2 字        ← 普通关键词，只报字数
```

这个计数走的是输入事件，**不等搜索那个 200 毫秒防抖**——边打边数位数，慢半拍就没用了。

**输入的是分类时，还会提示这个分类能按哪些特征找。** 光说一句"可以按特征筛"没用——失主得知道有哪些特征、能填什么值。所以直接把特征名和取值都摆出来，取值做成可点的按钮：

```
🔎 ☂️ 雨伞 还能按这些公开特征找——点一下加进搜索：
  [伞面颜色]  · 黑色 · 白色 · 灰色 · 蓝色 · 红色 · 粉色（等 11 项）
  [柄型]      · 直柄 · 弯柄 · 自动伸缩 · 折叠短柄
```

点一下就把这个值加进搜索词（搜索本来就支持空格分隔的多词「与」匹配），再点一下取消——等于把筛选器直接做进了搜索框。已经加进去的值会高亮。

匹配只认分类名（打「雨伞」「黑色雨伞」都算），**不做同义词**：搜「校园卡」不会提示「证件卡片」的特征，那需要一张"校园卡 = 证件卡片"的对照表，而那张表没法自动验证对错。这一点记在下面的已知限制里。

> 顺便一提：搜索词里全填 `*`（18 个）在规则上成立，效果等于"把有卡号的信息都捞出来"。这不是漏洞——匹配只代表这条信息**可能相关**，能不能拿到联系方式仍然要看认领验证答不答得对。

卡号不做筛选控件——一排 `350504************` 的按钮既看不懂也没法精确匹配，这一类靠关键词搜索。

**一条不写在代码里、但同样是硬规矩的约定：公开特征白名单同时是"出题禁区"。** 品牌既然公开了，验证题就不能再问品牌，否则就是给冒领者送分。`LF.QUESTION_TEMPLATES` 和演示数据都按这条重写过，并且有单元测试盯着（见下方"测试"一节）。

### 关于「认领验证」

这是本项目最有价值的一个设计，解决的是**冒领**问题：招领信息如果把联系方式直接公开，任何人都能看到，真正的主人反而可能被抢先。

第一版方案是"系统按物品分类预设问题、发布者只填答案、认领时随机抽 2 题手打答案"。实现之后发现两个绕不开的毛病：**判不准**（发布者写「深蓝色」，失主记得「藏青」，机器判错）和**能试探**（为了让失主知道错在哪，页面会指出答错的题，等于每答错一次就排除一个选项）。

所以第二版把这一块整体换成**纯客观题 + 限制次数**：

| 环节 | 规则 |
| --- | --- |
| 出题（拾得者） | 只允许**判断题**和**选择题**；题量 3–5 题（建议 4 题）；选择题 2–4 个选项并指定正确答案；**选项之间必须差别明显**（不能同时写「深蓝色」和「藏青」，也不能写「深蓝」和「深蓝色」）；可按物品分类插入出题模板再改 |
| 作答（认领者） | 一次性看到全部题目、**一次答完**再提交；每题点选项，没有自由文本 |
| 判定 | 系统统一判定，**全部答对才算通过**；未通过时只提示「回答的细节与描述不符」，**不告诉你是哪一题错** |
| 次数 | 最多答 **3 次**；答对不消耗次数，答错扣一次；发布者换了题目则重新给满 3 次 |
| 通关 | 显示发布者联系方式 + 生成认领凭证码 |
| 兜底 | 3 次全败后解锁【**申诉**】按钮，进入人工审核通道：认领者写下只有物主才知道的细节与联系方式，拾得者在「我的发布 → 人工审核」里判断，同意交还即解锁联系方式 |

**这套规则的适用范围是有边界的：只有"有公开特征可核对"的分类才出题。「其他」不出题**（它没有可锁的特征，硬出题只会让人把描述抄一遍），改成描述与照片直接公开的信任原则，见上文「其他」那一节。判定入口 `LF.allowVerifyFor()` 是这套边界唯一的开关。

**正确答案在任何对外数据里都不存在**——列表、搜索结果、详情页、答题页拿到的题目对象已经被数据层剥掉了 `answer` 下标（见 `js/store.js` 的 `toPublic()` 与 `publicQuestion()`），不是靠前端隐藏。认领记录 `claims` 与申诉记录 `appeals` 同样不会随信息公开，申诉明细只有发布者能看。这几条规则都有单元测试直接验证。

### 还有一个容易漏掉的口子：选项本身

改成客观题解决了"答案判不准"，但同一个毛病会从答案层搬到**选项层**：发布者把「深蓝色」和「藏青」当成两个选项，东西明明是藏青色的同学，看见「深蓝色」也会觉得说的就是自己那件，随手就选了——答错一次，还被系统判成"细节不符"。**含糊的选项和含糊的答案是同一类错误**，所以出题时也要拦：

- 两个选项属于同一组易混说法（「深蓝色」/「藏青」、「白色」/「米白色」）→ 拒绝发布；
- 一个选项包含另一个（「深蓝」/「深蓝色」、「图书馆」/「图书馆一楼」）→ 拒绝发布；
- 深浅分明的两档（「深蓝」/「浅蓝」）和不同色系（「黑色」/「灰色」）**不算易混**，不能误伤——误报一多，这条规则就会被人当噪音忽略掉。

易混词组表在 `js/config.js` 的 `LF.CONFUSABLE_GROUPS`，判定在 `js/store.js` 的 `confusableOptionPair()`。页面上是边打字边提示，不用等到提交才报错。

## 四、开发与测试

### 运行单元测试

双击 `test/test.html`（Chrome 打开）即可，离线可用。

测试覆盖的是**业务逻辑**，不依赖 DOM：`js/store.js` 采用「纯逻辑 + 注入式存储适配器」的设计——浏览器里注入 `localStorage`，测试里注入内存实现。因此测试不需要 jsdom，不需要起服务器，也不需要装 Node.js。

### 自检标记

每个页面渲染完成后会在 `<html>` 上写一个 `data-selftest` 属性，例如：

```html
<html data-selftest="PASS|page=home|cards=14">
```

开发时可以用命令行批量检查所有页面是否正常运行：

```bash
chrome --headless --disable-gpu --dump-dom "file:///路径/index.html"
```

失败时会变成 `FAIL:...`。这里有两个坑要单独说明：

- **浏览器里 JS 抛异常时进程退出码仍然是 0**，只看退出码判断不出页面有没有跑起来。
- 启动阶段就抛异常时，`markReady` 根本执行不到，结果是**页面里压根没有 `data-selftest` 属性**，而不是 `FAIL:...`。所以判断条件必须是"属性存在且以 PASS 开头"，不能写成"不包含 FAIL"。
- 本机已经开着 Chrome 时，直接调用会把请求转发给已有窗口、输出为空。**必须加一个独立的 `--user-data-dir`**。

### 首页的直达链接

首页支持 `?category=card&feature.brand=华为&area=library&type=lost` 这类参数。

除了分享方便，它还是首页筛选**唯一能被上面那套命令检查到**的入口：默认 `category` 是 `all`，特征筛选区根本不会渲染，光加载 `index.html` 是测不到它的。

### 第三方库

`test/lib/` 下的 Mocha 与 Chai 是从 npm 官方源下载后**随仓库一起提交**的浏览器版构建：

| 库 | 版本 | 为什么选这个版本 |
| --- | --- | --- |
| Mocha | 12.0.3 | 提供 `mocha.js` / `mocha.css` 浏览器构建，`<script>` 直接加载 |
| Chai | 4.5.0 | 5.x 起只提供 ES Module，而 `file://` 下 `type="module"` 会被 CORS 拦截 |

需要重新获取时执行 `python test/lib/_fetch-libs.py`。

## 五、技术选型说明

| 决定 | 原因 |
| --- | --- |
| 不用 ES Module，用经典 `<script>` 标签 | `file://` 协议下 `type="module"` 会因跨源限制加载失败。所有模块挂在 `window.LF` 命名空间下，按依赖顺序加载 |
| 不用任何前端框架 | 作业要求「下载后双击就能用」，引入框架必然带来构建步骤或网络依赖 |
| 数据存 localStorage | 无后端。写入前先检测存储是否可用（无痕模式、企业策略下会抛 SecurityError），依次降级到 sessionStorage、内存，并在页面顶部提示用户 |
| 照片压缩后再存 | localStorage 只有约 5MB，原图转 base64 会很快写满。统一缩到最长边 900px 并逐级降低质量，直到单张不超过 6 万字符 |
| 存储软上限 200 万字符 | 提前拦住写入，给出「去我的发布删除旧信息」这种能照做的提示，而不是等浏览器抛异常 |
| 种子数据写在 `js/seed.js` 里 | `file://` 下 `fetch()` 必然失败，演示数据不能放在 JSON 文件里靠请求加载 |

## 六、已知限制

- 没有账号体系（作业不要求实名认证），用本机生成的随机 id 判断「我的发布」。因此换浏览器、换电脑、清除浏览器数据都会看不到自己发布过的内容。
- 数据只存在本机，不同用户之间不共享——这是无后端方案的固有边界。带来的一个直接后果是：**申诉的提交与审核在同一台设备上完成**。在真实环境里，认领者的申诉应当提交到服务端、并在发布者那一端看到；本项目用同一份本地数据模拟了这条通道（发布者切换身份即可处理），README 与博客里如实说明。
- 认领尝试次数记录在信息上，而不是按认领人区分。同一条信息被答满 3 次后，其他人也只能走申诉通道。真实环境应按用户计数，本项目作为课程作业做了简化。
- 发布者修改验证题后，之前失败的次数会作废、重新给满 3 次——这是有意为之（换题等于换了一套验证），但也意味着发布者可以借此重置次数。
- 旧版本（隐藏特征方案）的数据会**就地迁移**：保留公开字段，停用自由文本答案，并在「我的发布」里提示发布者重新出题。自由文本答案无法自动变成客观题，我们选择不编造选项。
- **「其他」这一类没有防冒领闸门**：它不出验证题，描述和照片直接公开、联系方式直接可见，所以理论上谁先看到都能联系发布者。这是刻意的取舍（见上文「其他」那一节）：这个分类没有可锁的客观特征，硬出题只会让人把描述抄一遍。页面在发布、详情、我的发布三处都写明了这条代价，并提示"别把唯一凭据写进公开描述"。v3 时代这一类留下的验证题会在 `DATA_VERSION 3 → 4` 的迁移里被清掉。
- **加了公开特征之后，老记录的详情页会"看起来变空"**：它们既没有特征、描述又按新规则不再展示，只剩标题和地点。迁移会补一个空的 `features`，详情页在"没有特征"时会**回退去展示那段老描述**（见 `page-detail.js` 的 `showsDescription`），所以不会真的一片空白；发布者编辑一次、补上特征之后描述才让位。我们没做"把老描述自动塞进特征字段"的迁移——那只能靠猜，等于编造数据。
- 特征筛选的取值是白名单，所以失主只能按"蓝色"找，不能表达"藏青"。这是刻意的取舍：可筛选和可描述二者只能取一个，我们选了前者（`LF.CONFUSABLE_GROUPS` 里那些同色系易混说法，在出题时另有拦截）。
- 搜索页的分类特征提示只认分类名，**不做同义词**：搜「雨伞」「黑色雨伞」会提示，搜「伞」「校园卡」不会。补一张同义词表不难，但那张表本身没法自动验证对错，所以宁可先不做。
- 繁简中文不互通（搜「校園卡」找不到「校园卡」）。做个简繁转换表能用十几行解决，但会引入一份无法测试覆盖的映射数据，性价比不高，故不做。
