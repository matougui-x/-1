# PSP 表格

> ## ⚠️ 请先读这一段
>
> **「实际耗时」这一列必须由你们两个人各自按真实记录填写，不要照抄下面的数字。**
>
> 本次作业的题目说明里专门批评了一种情况：「有一份作业的 PSP 表中，各项预估耗时与实际耗时完全一致」，并指出 PSP 的作用是**帮助你们发现哪些工作低估了、哪些环节发生了返工**。所以：
>
> - 「预估耗时」可以直接用下面这份（它是一份合理的开发前计划，记不清就照用）；
> - 「实际耗时」请翻你们的聊天记录、编辑器历史、GitHub 的 commit 时间戳（`git log --pretty=%ad --date=iso` 就是现成的时间线），如实填；
> - 「差异说明」栏要写**原因**，不要写「基本符合」。承认某一步超时并分析原因，比全表数字漂亮得分更高。
>
> 最后一行「合计」和文末的「用时分析」也要跟着实际数字一起改。

## 用时分析（请在填完实际数字后再写）

填写时建议围绕下面几个问题展开，这几条正是题目说明里点名的关注点：

1. **哪一步明显超出预估？为什么？**
   例如：认领验证的「抽题—作答—比对」跨了两个页面，中途发现页面之间不共享内存，需要把结果落一次盘才能传给结果页，返工重写了这部分。

2. **有没有发生返工？返工的原因是什么？**
   例如：最初把「全角转半角」的归一化用在了存储环节，导致用户写的「微信：zhangmy2023」被改写成「微信:zhangmy2023」，中文标点全被替换，后来把「用于比较的归一化」和「用于存储的清理」拆成了两个函数。

3. **测试花了多少时间？值不值？**
   例如：写测试的时间占了相当比例，但确实抓到了真实 bug（有一处点击「标记已归还」时变量引用错了作用域，界面上没有任何反应，看代码很难发现，写交互测试时一点就暴露了）。

4. **如果重做一次，你会怎么安排？**
   例如：先写数据层和测试，再做界面；而不是先堆页面再补测试。

> 【以上四条只是提示，请按你们的真实情况改写，不要照抄】

## 附：怎么快速导出 commit 时间线

如果按功能分批提交过，可以用 Git 的提交时间反推各阶段的实际耗时：

```bash
git log --pretty=format:"%ad  %s" --date=format:"%m-%d %H:%M"
```

输出形如：

```
10-05 14:20  数据层：校验与搜索
10-05 19:45  数据层：状态流转与权限
10-06 10:12  首页：筛选与列表渲染
```

两条相邻提交的时间差，就近似对应了中间那段时间的投入。
